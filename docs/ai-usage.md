# Where AI Is Used

The agent is a deterministic data pipeline with an LLM at the edges. This page lists every place a
model is or could be involved, what it decides, and what guards its output.

## Principle

The mechanical parts of a migration (discovery, blocker detection, sizing, topology mapping,
rendering Terraform) are rule-driven and reproducible. The model is used where the input is
ambiguous or the output is prose for a human. Nothing the model produces is executed or written
to output without passing the same deterministic gates as everything else.

## Today

| Where | What the model does | Mode | Guards |
|---|---|---|---|
| Review notes (`reporter`) | Writes the run summary: blockers, reasons, remediations, validation outcome, next actions | every mode when an LLM provider is configured; deterministic fallback text otherwise | Prose only, never executed |
| HCL generation (`hcl_generator`, `--mode llm`) | Writes the Terraform from the CIM | opt-in | Structured JSON output, path policy, code-execution deny-list, provider allow-list, terraform validate, tflint, OPA |
| HCL repair (`--mode hybrid`) | Receives the deterministic render's validation errors and produces a corrected file set | opt-in | Same gates as llm mode; only runs when the deterministic render fails validation |

The default `deterministic` mode makes no model calls at all for generation.

## Planned (Phase 2 and later)

| Where | What the model would decide | Human in the loop |
|---|---|---|
| Quarantine explanations | Per-VM plain-language explanation of each blocker and the remediation options (decrypt, convert RDM, detach shared disk) | Read-only |
| Guest OS to image mapping | Suggest a target image family when the lookup table has no entry (for example CentOS 7 at end of life) | Operator approves before the mapping is used |
| Tag and metadata derivation | Turn vSphere annotations, custom attributes and tags into cloud tags and ownership metadata | Operator reviews in the CIM editor |
| Wave and cutover planning | Propose migration waves and ordering from dependency data once collected | Operator edits the plan |
| UI copilot | Answer questions about a run: why a VM was blocked, what a network maps to, what changes if a blocker is cleared | Read-only over run state |

## Deliberately not AI

- Blocker detection, sizing, topology and placement mapping: rules in `cim/blockers.py`, `providers/*/sizing_table.py`, the translator and the renderers.
- Security policy: OPA rules over parsed HCL in `hopshift/validation/policies/`.
- The CIM itself: typed, validated, diffable; it is what a human edits, so it must not be regenerated by a model.

## Model and client settings

Configured in `config.yaml` under `llm`. The Anthropic client uses structured outputs, a cacheable
prompt prefix, transient-error retries, server-side refusal fallbacks and records token usage per
call in the run messages. See `docs/configuration.md`.
